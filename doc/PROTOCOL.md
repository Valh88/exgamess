# PROTOCOL — спецификация клиент-серверного протокола ExGames

Спецификация для клиентов на любом языке (Haxe, C++, Rust, C#, JS...).
Транспорт — HTTP (JSON) + WebSocket (бинарные кадры). Коды операций
фиксированы; развитие протокола — только новыми кодами.

## Конвенции msgpack (важно для Haxe)

* все ключи map — **строки**;
* токены/идентификаторы — ASCII-строки;
* ext-типы не используются.

## 1. HTTP: аккаунты и матчмейкинг

### Регистрация / вход

```
POST /api/auth/register   {"username": "ann", "password": "secret123"}
POST /api/auth/login      {"username": "ann", "password": "secret123"}
```

Ответ `200`:

```json
{
  "token": "SFMyNTY...",
  "user": {"id": 1, "username": "ann", "roles": ["player"], "banned_at": null}
}
```

Ошибки: `401` (неверные креды), `403` (бан), `422` (`{"errors": {...}}`).

Токен передаётся во все далее как заголовок `Authorization: Bearer <token>`.

### Матчмейкинг (шаг 1 двухфазного join)

```
POST /api/matchmake/join_or_create/:room_name
POST /api/matchmake/create/:room_name
POST /api/matchmake/join/:room_name
POST /api/matchmake/join_by_id/:room_id
POST /api/matchmake/reconnect/:room_id
```

Тело (необязательно): `{"options": {...}}` — ключи, объявленные в
`filter_by` типа комнаты, участвуют в поиске и попадают в метаданные.

Ответ `200` — **seat reservation**:

```json
{"room_name": "arena", "room_id": "Ab3xYz9Kp", "session_id": "sKd83jdDk2m1"}
```

Бронь действует 15 секунд. Ошибки: `404` c кодом `520` (тип комнаты не
зарегистрирован), `521` (нет комнаты для `join`), `523` (комната заполнена),
`423` (комната закрыта), `522` (комната не найдена — для `join_by_id`).

`join_by_id` резервирует место в конкретной комнате по её `room_id` (без
поиска по типу; `room_name` в ответе может быть `null` для комнат вне
матчмейкера).

`reconnect` — шаг 1 reconnect-флоу: проверка reconnection-токена после
не-согласованного обрыва. Тело: `{"session_id": "...", "reconnection_token": "..."}`
(`session_id` можно опустить — токен самодостаточен). Ответ `200`:

```json
{"room_id": "Ab3xYz9Kp", "session_id": "sKd83jdDk2m1", "reconnection_token": "..."}
```

Ошибка: `404` с кодом `522` (токен невалиден/истёк — окно переподключения
`reconnect_ttl`, по умолчанию 30 секунд, уже закрыто).

### Листинг комнат

```
GET /api/rooms[?room_name=arena]
```

## 2. WebSocket: игровой канал

### Подключение (шаг 2)

```
GET ws://host:port/ws/:room_id?sessionId=:session_id
GET ws://host:port/ws/:room_id?sessionId=:session_id&reconnectionToken=:token
```

Сервер валидирует бронь. Успех: клиент получает кадр `join_room`
(`10`). Ошибка: кадр `error` (`11`) с кодом `522` и закрытие.

Второй вариант — шаг 2 reconnect-флоу: транспорт переподключается к живой
сессии по reconnection-токену (без новой брони); `session_id` сохраняется,
логики повторный join не получают.

### Формат кадра

```
+----------+---------------------------+
| opcode   |  payload (msgpack)        |
| u8       |                           |
+----------+---------------------------+
```

Однобайтовый кадр: `LEAVE_ROOM` (12) — payload отсутствует. `PING` (18)
тоже однобайтовый, но может нести payload для синхронизации времени (ниже).

### Опкоды

| код | имя | направление | payload |
|----:|-----|-------------|---------|
| 10 | `JOIN_ROOM` | сервер → клиент | `{"room_id": "...", "session_id": "...", "reconnection_token": "..."}` |
| 11 | `ERROR` | сервер → клиент | `{"code": <int>, "message": "...", "request_id"?: <int>}` — `request_id` присутствует, когда ошибка отклоняет конкретный `ROOM_REQUEST` |
| 12 | `LEAVE_ROOM` | оба | — |
| 13 | `ROOM_DATA` | оба | `{"t": <type>, "p": <payload>}` — тип: строка или int |
| 14 | `ROOM_STATE` | сервер → клиент | полный снапшот состояния комнаты |
| 15 | `ROOM_STATE_PATCH` | сервер → клиент | дельта состояния `{"ops": [...]}` — см. [DELTA_SYNC.md](DELTA_SYNC.md) |
| 18 | `PING` | оба | без payload — однобайтовый (keepalive/RTT); с payload — синхронизация времени и RTT: клиент шлёт `{"t": <свои монотонные ms>, "rtt"?: <int ms — последний замер>}`, сервер эхирует `{"t": ..., "ts": <unix-ms сервера>}` (источник `Room.serverNow()` в SDK) и складывает `rtt` в клиента (EMA; читается `Room.client_rtt/2`, telemetry `[:ex_games, :room, :ping]`); голый `18` остаётся валидным (обратная совместимость) |
| 21 | `ROOM_REQUEST` | клиент → сервер | `{"i": <request_id>, "t": <type>, "p": <payload>}` |
| 22 | `ROOM_RESPONSE` | сервер → клиент | `{"i": <request_id>, "p": <payload>}` |
| 23 | `ROOM_ENTER` | клиент → сервер | gateway: `{"room_id": "...", "session_id": "...", "reconnection_token"?: "..."}` — вход в комнату на общем сокете (см. «Gateway») |
| 25 | `MUX` | оба | gateway: `{"r": <room_id>, "f": <bin — внутренний кадр как есть>}` |
| 26 | `MUX_CLOSED` | сервер → клиент | gateway: `{"r": <room_id>, "code": <int>, "message": "..."}` — канал комнаты закрыт, сокет жив |

Клиент после получения `JOIN_ROOM` может отправить свой `JOIN_ROOM` (ack) —
сервер его игнорирует (для совместимости с существующими клиентами).

### Порядок при входе

1. сервер → `JOIN_ROOM` (10) — `reconnection_token` в payload нужен клиенту
   для переподключения после обрыва (при reconnect клиент получает НОВЫЙ
   токен — ротация)
2. сервер → `ROOM_STATE` (14), если у комнаты задано состояние
3. далее — обычный обмен `ROOM_DATA`

### Дельта-синхронизация состояния

Комната с опцией `state_sync: :delta` шлёт состояние так:

1. при входе клиента — полный `ROOM_STATE` (14) со снапшотом;
2. далее на каждом изменённом тике — `ROOM_STATE_PATCH` (15) только
   с изменениями; изменений нет — кадр не отправляется;
3. при reconnect клиенту снова уходит полный `ROOM_STATE` (resync).

Тело патча — msgpack-объект `{"ops": [...]}`; операция:

```elixir
%{"p" => ["players", "sKd8", "x"], "v" => 10}   # установить по пути
%{"p" => ["players", "ann"],       "d" => true}  # удалить ключ
```

Путь — массив строковых ключей от корня состояния (`[]` — корень);
отсутствующие промежуточные узлы клиент создаёт. Операции —
«присваивание значений»: повторное применение безопасно. Списки и
прочие не-map значения патчатся целиком по пути.

Режимы комнаты: `state_sync: :snapshot` (по умолчанию — всегда полный
кадр) или `:delta`. Реализация: `ExGames.Room.StateDiff` (сервер),
`gamessa.StatePatch` (Haxe SDK).

### Reconnect после обрыва

Не-согласованный обрыв (закрытие сокета без кадра `LEAVE_ROOM`) не удаляет
клиента: комната держит сессию в слоте reconnection в течение
`reconnect_ttl` (опция комнаты, по умолчанию 30 секунд), место остаётся
занятым. Клиент:

1. `POST /api/matchmake/reconnect/:room_id` с токеном → `session_id`;
2. `WS /ws/:room_id?sessionId=…&reconnectionToken=…` → сервер шлёт
   `JOIN_ROOM` (10) с новым токеном + полный `ROOM_STATE` (14).

На gateway-сокете шаг HTTP не нужен — `session_id` известен клиенту:
повторный `ROOM_ENTER` (23) с `reconnection_token` делает reattach.

По истечении окна клиент удаляется с причиной `:closed` (кадр `LEAVE_ROOM`
от клиента или `reconnect_ttl: false` отключают этот механизм: обрыв сразу
вызывает `handle_leave`).

## 2a. Gateway: несколько комнат одним WebSocket

`GET /ws/:room_id` открывает сокет одной комнаты. Альтернатива —
мультиплексированный сокет `GET /ws` (без room_id): все комнаты одного
клиента живут на одном соединении, кадры адресуются конвертами.

Флоу:

1. HTTP-шаг тот же (бронь матча/комнаты, `session_id` на комнату);
2. `GET ws://host:port/ws` — сокет без комнаты;
3. `ROOM_ENTER` (23) — вход: без `reconnection_token` — attach по брони,
   с токеном — reattach (reconnect-флоу, ротация токена);
4. сервер отвечает обычным `JOIN_ROOM` (10) и `ROOM_STATE` (14) — но в
   `MUX`-конверте (25): `{"r": <room_id>, "f": <кадр как есть>}`;
5. далее все комнатные кадры (`ROOM_DATA`, `ROOM_REQUEST`, `PING` с RTT,
   `LEAVE_ROOM`, …) ходят внутри `MUX` без изменений — внутренний кадр
   не перекодируется;
6. закрытие канала — `MUX_CLOSED` (26): кик, комната закрылась, отказ
   входа (`"enter failed: …"`, `"already entered"`). Сокет при этом жив,
   остальные комнаты не затронуты.

Правила:

* повторный `ROOM_ENTER` в ту же комнату на одном сокете → `MUX_CLOSED`
  c кодом 522 (`already entered`);
* голый `PING` (18) на сокете — keepalive самого соединения (эхо);
  пер-комнатные PING/PONG ходят в конвертах (RTT/часы как обычно);
* невалидный внешний кадр → кик всего сокета (4002), как и на `/ws/:room_id`;
* обрыв сокета: сервер видит DOWN транспортов всех комнат клиента и держит
  их reconnect-слоты; повторное подключение — снова `ROOM_ENTER` с токенами.

Реализация: сервер — `ExGames.Room.Gateway` (канал-прокси на каждую пару
gateway×комната, комната-GenServer не меняется) + `ExGamesWebWeb.GatewaySocket`;
клиент — `gamessa.Gateway`/`gamessa.transport.MuxChannel` (режим
`client.useGateway`). Совместимость: опкоды 23/25/26 — старый сервер их
не знает (invalid frame → кик), а старый клиент на `/ws` не заходит.

### request/response

Клиент отправляет `ROOM_REQUEST` со своим `request_id` (уникальный int);
сервер отвечает `ROOM_RESPONSE` с тем же `request_id` или `ERROR`.

### Коды ошибок ERROR

| код | смысл |
|----:|-------|
| 520 | тип комнаты не зарегистрирован |
| 521 | неподходящие критерии/нет комнаты |
| 522 | комната/сессия не найдены (нет брони) |
| 523 | join отклонён комнатой (заполнена/закрыта) |
| 525 | ошибка аутентификации |
| 526 | внутренняя ошибка / неизвестный request |

### Коды закрытия WebSocket

| код | смысл |
|----:|-------|
| 4000 | нормальное закрытие (клиент ушёл / комната закрыта) |
| 4001 | выключение сервера |
| 4002 | ошибка протокола / кик / превышение rate-limit |

### Ограничения

* rate-limit по умолчанию 120 кадров/с на соединение (превышение → кик 4002);
* текстовые WS-кадры игнорируются — только бинарные.

## 3. Нативная игровая логика (сервер ↔ логика)

Отдельный канал между сервером и процессом логики (адаптеры Port/TCP).
Фрейминг: `u32 length-prefix + msgpack`. Тот же бинарник работает через
stdio и TCP. Эталонная реализация — `apps/ex_games/priv/native_echo.exs`.

Запросы сервера:

```
{"op": "init", "args": [...]}
{"op": "call", "fn": "имя", "args": [...], "state": <state>}
{"op": "tick", "dt": <мс>, "state": <state>}
```

Ответы логики:

```
init: {"ok": true, "state": <state>}
call: {"ok": true, "result": ..., "state": <state>} | {"ok": false, "error": "..."}
tick: {"ok": true, "state": <state>} | {"ok": false, "error": "..."}
```

Состояние передаётся в каждом запросе (владелец — комната): краш нативного
процесса не теряет игру.
